The protocol does not invent numbers. It reads numbers off public pages. Four sources, two metrics, no opinion. The full methodology lives in [Data Source Methodology](/trust/data-source-methodology); this page is the operational summary.

## The four sources

| Source | Used by | Metric | What is read |
|---|---|---|---|
| xvideos | Stars (subset) | view count per subject page | total cumulative views |
| xnxx | Stars (subset) | view count per subject page | total cumulative views |
| pornhub | Stars (subset) | view count per subject page | total cumulative views |
| chaturbate | Cams | concurrent viewer count per room | live viewer count |

Each pair in the catalog is bound to one source at deploy time. A Stars pair reads from one of xvideos, xnxx, or pornhub depending on which platform hosts the subject. A Cams pair always reads from chaturbate.

The source per pair is published with the catalog. It is not a runtime decision; it is part of the on-chain Market PDA configuration.

## What gets measured

**Stars — F1 gain race.** The Goldilock oracle network reads the cumulative view count for each subject at the round's open time and again at the round's close time. The difference is the gain.

```
gain = views_at_close − views_at_open
```

A subject's absolute view count does not matter. The growth over four hours does.

**Cams — F1 gain race + F2 viewer total.**

For F1, the same gain-race math applies but the underlying metric is concurrent-viewer cumulative time-on-page or comparable growth signal — fixed per pair, published in the methodology.

For F2, the oracle takes interval readings of concurrent viewers across the two-minute window, and aggregates by the rule fixed at deploy time (peak or mean). The aggregation rule is published per market. It does not change retroactively.

## How readings are taken

Each oracle node performs its own scrape or API call against the source. No node trusts another node's reading. Quorum is reached when enough independent readings agree. See [Settlement Rules](/product/settlement-rules).

Readings are timestamped, signed, and published from the oracle node. Anyone can re-derive the resolution from the same readings. The math is the same math; the inputs are the same inputs; the result is the same result. The protocol is provably fair in the sense that the inputs and the algorithm are both public — there is no closed-source RNG, no opaque "house" judgement. There is a number from a webpage and a subtraction.

## What the protocol does not measure

- **Subjective quality.** Nobody rates the videos. Nobody scores the performances. The metric is mechanical.
- **Engagement signals beyond views.** No likes, no comments, no time-on-page, no fan-club tier. Just the count.
- **Demographics or geography.** The protocol reads what the page shows; it does not partition by audience.
- **Aggregate platform health.** A subject's view count is what it is on the source page. If the source under-reports globally, the round still resolves on what the page said.

The metric is shallow on purpose. A shallow metric is a verifiable metric.

## When the source breaks

Tube sites have rate limits, outages, layout changes, and policy shifts. Each is handled by the same rule: if the oracle cannot read what it needs to read, the round voids. See [Refund Policy](/product/refund-policy) for the full taxonomy.

Specific failure modes:

- **Source goes down mid-round.** No close reading possible. Round voids.
- **Source rate-limits the oracle network.** Insufficient readings for quorum. Round voids.
- **Source changes its API or HTML layout in a way that breaks the parser.** Reading invalid. Round voids. The market is paused until the parser is updated and the change is documented.
- **Source removes a subject mid-round.** No reading possible at close. Round voids. The subject is then handled per [Subject Removal Policy](/trust/subject-removal-policy).
- **Source returns inconsistent data across nodes — disagreement at the integer level.** Quorum fails. Round voids.

## What the protocol publishes

Every settlement publishes:

- The pair index.
- The source.
- The open-time reading and close-time reading (F1) or the interval readings and aggregate (F2).
- The declared winner.
- The aggregated oracle signature.
- The on-chain settlement transaction.

These are the receipts. They are not summaries; they are the inputs the oracle used. The full readings live on the oracle node and are mirrored to the indexer database.

## Why public tube metrics

Public metrics have three properties the protocol needs:

1. They exist. No private API key required to read them.
2. They are verifiable. A bettor with a browser can confirm a count.
3. They are difficult to manipulate at oracle scale — manipulation requires moving the underlying platform's metric, which is harder than spoofing a private feed.

They also have one property that complicates everything: they depend on a third party we do not control. The third party can change its mind about whether the metric is public, accurate, or stable. The void path exists because we know this. See [Audit & Mainnet Roadmap](/trust/audit-and-mainnet-roadmap) for how source resilience is part of the mainnet gate.
