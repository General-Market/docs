A tick is a discrete time window — the block's `tickDuration` (1 second to 30 days). At the end of every tick, the oracle resolves every market and redistributes the pot.

- **Resolution cycle:** fetch prices → determine UP/DOWN/FLAT → match winners against losers → update balances → BLS-sign → submit on-chain
- **Side matching:** parimutuel (mutual betting — winners split the losers' pot proportionally)
- **Reveal window:** default 600s. Miss it and you are voided for that tick
- **Multipliers:** early commitment + persistence boost effective stake, capped at balance
- **Six possible outcomes per market:** Up, Down, Flat, Cancelled, AllSameSide, AllLosers (last four refund all stakes)

## What Happens Every Tick

Every tick, the system resolves all markets in a block:

1. Fetch start/end prices for each market
2. Determine outcome (UP / DOWN / FLAT)
3. Match winners against losers (parimutuel)
4. Update player balances
5. BLS-sign results across oracles

Check your balance after resolution: `GET /vision/balance/{blockId}/{playerAddress}`

## What Is a Tick?

A tick is a discrete time window. The block's `tickDuration` (in seconds) sets the length. Tick numbering starts from `createdAtTick` — the tick number when the block was created.

```
Tick N starts at: (createdAtTick + N) * tickDuration
Tick N ends at:   (createdAtTick + N + 1) * tickDuration
```

For a block created at tick 1000 with `tickDuration = 600` (10 minutes):

| Tick | Starts At | Ends At |
|------|-----------|---------|
| 0 | 600,000 | 600,600 |
| 1 | 600,600 | 601,200 |
| 2 | 601,200 | 601,800 |

<Info>
Tick numbers are computed from Unix timestamps: `currentTick = block.timestamp / tickDuration`. The `createdAtTick` anchors the block's tick numbering to the blockchain's time.
</Info>

## Resolution Cycle

When a tick is due, the oracle engine runs a deterministic pipeline:

### Step by Step

**1. Check due blocks.** The tick scheduler polls at regular intervals (default: 1 second) and identifies blocks whose current tick has ended plus the reveal window has elapsed.

**2. Filter active players.** Only players with a non-zero balance participate. Zero-balance players are skipped.

**3. Check bitmap reveals.** Each active player's bitmap must have been revealed to the oracle (submitted via `POST /vision/bitmap`). Players who did not reveal are **voided** -- their balance stays unchanged and they do not participate in side matching.

**4. Compute multipliers.** Each revealed player gets an early multiplier and a commitment multiplier applied to their stake. See [Multipliers](#multipliers) below.

**5. Resolve each market.** For every market in the block:
   - Fetch the start price (from the previous tick's end price) and end price (current snapshot).
   - Check that price data is not stale (older than the configured threshold, default 300 seconds).
   - Compute the percentage change: `(end - start) / start * 100`.
   - Determine the outcome using the market's resolution type. See [Resolution Types](/docs/blocks/concepts/resolution-types).
   - Decode each player's bitmap bit for this market index (1 = UP, 0 = DOWN).
   - Run parimutuel side matching to compute payouts.

**6. Aggregate balance changes.** Sum each player's deltas across all markets to produce a single net balance change per player.

**7-8. BLS consensus and on-chain submission.** Oracles sign the results with BLS keys and submit on-chain for claiming.

## Market Outcomes

Each market in a tick resolves to one of six outcomes:

| Outcome | Meaning | Effect |
|---------|---------|--------|
| **Up** | Price increased (meeting the resolution type's threshold) | UP side wins, DOWN side loses |
| **Down** | Price decreased (meeting the threshold) | DOWN side wins, UP side loses |
| **Flat** | Price change did not meet any threshold | Full refund to all players |
| **Cancelled** | Price data missing or stale | Full refund to all players |
| **AllSameSide** | All players picked the same side (no opponents) | Full refund to all players |
| **AllLosers** | Nobody picked the winning side | Full refund to all players |

### Parimutuel Side Matching

For markets with a clear winner (Up or Down), the parimutuel algorithm (parimutuel = mutual betting; winners split the losers' pool proportional to stake) distributes the pot:

1. Split players into UP and DOWN sides based on their bitmap bits.
2. Compute total effective stake for each side.
3. **Matched amount** = min(UP total, DOWN total). The smaller side is fully matched; the larger side has excess refunded.
4. **Winners** receive their matched stake back plus a proportional share of the losers' matched pool.
5. **Losers** forfeit their matched stake; unmatched excess is refunded.

```
Example: UP side = 300 USDC, DOWN side = 100 USDC, outcome = UP

Matched = min(300, 100) = 100 USDC

UP player (300 stake):
  matched_stake = 300 * 100 / 300 = 100
  refund = 300 - 100 = 200
  payout = 100 * 2 = 200
  Total received: 200 + 200 = 400 (profit = 100)

DOWN player (100 stake):
  matched_stake = 100 * 100 / 100 = 100
  refund = 0
  payout = 0
  Total received: 0 (loss = 100)
```

<Info>
Total payout always equals total effective stakes. No USDC is created or destroyed — it is purely redistributed between winners and losers.
</Info>

### AllSameSide

If every player in a market picks the same side, there are no opponents to match. All stakes are refunded. A parimutuel market needs disagreement — without two sides, there is no pot.

### AllLosers

If a resolution type with a threshold (e.g., `UP_30`) returns a result where neither side's threshold is met, the outcome is `Flat` and all stakes are refunded. `AllLosers` is a separate edge case kept in the matching algorithm for robustness.

## Multipliers

Two multipliers amplify the stake before parimutuel matching: early commitment and persistence. Both are capped — see below.

### Early Multiplier

Rewards committing before the tick opens. The earlier you join, the more your stake is amplified:

```
early_mult = 1 + min(time_before_tick, tick_duration)^2 / tick_duration^2
```

| When You Join | Early Multiplier |
|--------------|-----------------|
| At tick start | 1.0x |
| Half a tick before | 1.25x |
| One full tick before | 2.0x |
| Two or more ticks before | 2.0x (capped) |

### Commitment Multiplier

Rewards staying through many ticks. The curve is logarithmic — persistence is rewarded, but the marginal gain shrinks over time:

```
commitment_mult = log10(ticks_committed + offset)
```

With the default offset of 9:

| Ticks Committed | Commitment Multiplier |
|----------------|----------------------|
| 1 | log10(10) = 1.0x |
| 11 | log10(20) = 1.3x |
| 91 | log10(100) = 2.0x |
| 991 | log10(1000) = 3.0x |

### Effective Stake

```
effective_stake = stake_per_tick * early_mult * commitment_mult
```

Effective stake is capped at the player's current balance. You cannot risk more than you have deposited.

## Commitment Offset

The default **commitment offset** is 9. This parameter shifts the commitment multiplier's log curve so that the first tick starts at exactly 1.0x (since `log10(1 + 9) = log10(10) = 1.0`). Without the offset, a single tick would produce `log10(1) = 0`, which would zero out the effective stake.

## Reveal Window

After a tick ends, oracles wait the **reveal window** (default 600 seconds) before resolving. The window gives players time to submit their bitmap reveals.

```
Tick ends at: T
Reveal deadline: T + 600 seconds
Resolution happens after: T + 600 seconds
```

<Warning>
If a player does not reveal their bitmap before the window closes, they are voided for that tick. Balance unchanged, no winnings.
</Warning>

After the reveal window expires, bitmaps become public and can be queried via the API:

```
GET /vision/reveal/{block_id}/{tick_id}
```

This endpoint only returns data after the reveal deadline. Before that, it returns `403 Forbidden`.
