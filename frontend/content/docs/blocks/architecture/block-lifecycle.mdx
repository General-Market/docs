# Block Lifecycle

A Vision block runs through nine phases — from raw price ingestion to on-chain settlement. Three oracles must agree at every step. The contract verifies their agreement before any state changes.

- **Phases 1–2** — data-node fetches prices and proposes a block config every 60s.
- **Phases 3–4** — oracles discover the config, BLS-sign it, create the block on L3.
- **Phase 5** — players join with a sealed bitmap commitment (`keccak256`).
- **Phases 6–8** — oracles resolve each tick, BLS-sign the settlement, contract pays out.
- **Phase 9** — settlement outcomes feed back into the next threshold calibration.

**BLS** = Boneh-Lynn-Shacham, a signature scheme where signatures aggregate into one. **keccak256** = Ethereum's hash function. **Bitmap** = packed prediction bits, one per market.

## Phase 1: Market Data Ingestion

The data-node polls roughly 100 external sources — CoinGecko, weather APIs, FRED, Bloomberg, transit networks, election trackers — each on its own schedule. One `SyncEngine` per source, staggered, rate-limited, circuit-broken. Each row lands in two tables:

- **`market_prices`** — full history, 365-day retention.
- **`market_prices_latest`** — deduplicated snapshot, one row per `(source, asset_id)`, indexed for fast reads.

Each oracle runs its own data-node instance. Three independent databases polling the same APIs. If one data-node returns a bad price, the other two outvote it.

A fourth read-only data-node serves the frontend and bot APIs. It holds no signing key and cannot influence resolution.

---

## Phase 2: Block Config Generation

Every 60 seconds the `BlockEngine` builds a recommended config per source. The work is threshold calibration — finding the price-change boundary that splits outcomes 50/50.

### Three-Stage Threshold Computation

The engine wants half of future ticks to resolve UP, half DOWN. It tries four methods, falling through on failure.

**Stage 1 — median of past settlements.** Query `block_settlements` for the last N actual price changes per asset. Take the median (`PERCENTILE_CONT(0.5)`). Half of future values should exceed it, half should not. Primary method when history exists.

**Stage 2 — last settlement change.** No history yet. Use the most recent block's actual change and apply volatility bands:

| Change | Resolution | Threshold |
|--------|-----------|-----------|
| < 0.3% | `flat_x` | 30 bps |
| 0.3–3% | `up_x` | 30 bps |
| 3–30% | `up_300` | 300 bps |
| > 30% | `up_3000` | 3000 bps |

**Stage 3 — 24h price history.** No settlement history at all. Compute the 24-hour high/low range and apply the same bands.

**Stage 4 — source default.** Last resort. Use the source's hardcoded `zero_trend_type` and minimum threshold.

### Healthy Asset Selection

The engine reads `market_prices_latest` and keeps only assets that pass three filters:

- Price fresher than 10× the source's sync interval.
- Price greater than zero.
- Sorted by `asset_id` (deterministic ordering across oracles).

Cap: 8,192 markets per block. The on-chain bitmap is 1,024 bytes.

### Config Hash

The config is sealed with a deterministic hash:

```
market_hashes = [keccak256(abi.encode(asset_id, resolution_type, threshold_bps)) for each market]
markets_root  = keccak256(concat(sorted(market_hashes)))
config_hash   = keccak256(abi.encode(source_id, tick_duration, lock_offset, markets_root))
```

Oracles sign this hash. Any difference in market selection, ordering, or threshold produces a different hash, and consensus fails.

## Phase 3: Oracle Discovers Config

The oracle's lifecycle manager runs one heartbeat per source, staggered to avoid a thundering herd. Each heartbeat:

1. Fetches the latest recommended config from `GET /blocks/recommended`.
2. Extracts `config_hash`, `tick_duration`, `lock_offset`, and the full market list.
3. Records intent in the `vision_block_lifecycle` Postgres table.

Every heartbeat does two things at once: it creates the next block, and it resolves the previous one.

---

## Phase 4: BLS Consensus and On-Chain Creation

Only the leader (node index 0) submits on-chain. The other oracles co-sign.

### Leader Flow

1. **Construct the BLS message:**
   ```
   message = keccak256(abi.encode(
       chainId,
       visionAddress,
       "CREATE_BLOCK",
       sourceId,
       configHash,
       tickDuration,
       lockOffset
   ))
   ```

2. **Sign** with the leader's BLS private key.

3. **Broadcast** a `VisionCreateBlockProposal` via P2P to all followers.

4. **Collect co-signs.** Wait up to 30 seconds. Each follower verifies the proposal independently — same config hash, same parameters — and returns a BLS signature. The leader collects them until threshold is met: `ceil(2n/3)`. With three oracles, that is two signatures.

5. **Aggregate.** Collected signatures merge into a single aggregated BLS signature. A signer bitmask records which oracles participated.

6. **Submit on-chain:**
   ```solidity
   vision.createBlock(
       sourceId, configHash, tickDuration, lockOffset,
       blsSignature, referenceNonce, signersBitmask
   )
   ```

7. **Parse receipt.** The `BlockCreated` event contains the on-chain `blockId` — the block's permanent ID.

### Follower Flow

Followers never submit. They receive the leader's P2P proposal, verify it against their own data-node's recommended config, sign if it matches, and send the signature back. Once the leader submits, each follower's chain listener detects the `BlockCreated` event on L3 and registers the block in its local scheduler.

## Phase 5: Players Join

A player calls `joinBlockDirect` on the Vision contract:

```solidity
vision.joinBlockDirect(blockId, configHash, depositAmount, stakePerTick, bitmapHash)
```

- USDC moves from the player's wallet to the contract.
- `bitmapHash` is a `keccak256` commitment — the predictions, sealed.
- The lock window blocks joins during the final `lockOffset` seconds of a tick.

The oracle's chain listener detects the `PlayerJoined` event and registers the player in the in-memory scheduler. The player then submits the raw bitmap bytes to the oracle API (`POST /vision/bitmap`); the oracle hashes them and checks against the on-chain commitment.

### Two-Slot Bitmap Model

Each player has two bitmap slots per block:

| Slot | Purpose |
|------|---------|
| **Pending** | Where new bitmap submissions land during the current tick |
| **Active** | Where the resolver reads from at tick boundary |

At every tick boundary, pending promotes to active. A player who submits nothing keeps the previous bitmap. A player who never submitted is voided — full deposit refund, no participation.

Each bitmap carries its own `config_hash`. A config update between submission and resolution cannot scramble market positions: bit 0 stays the market the player intended.

## Phase 6: Tick Resolution

When the heartbeat fires and a `previous_block_id` is ready, the oracle runs a deterministic six-step pipeline.

### Step 1: Gather State

```rust
scheduler.get_block_state(block_id) → (Block, Vec<PlayerPosition>)
```

### Step 2: Fetch Prices

The oracle queries the data-node for the market config (`GET /blocks/config/:hash`) and a price snapshot (`GET /vision/snapshot`). For each market:

- **End price** — latest snapshot value, scaled to 18 decimals.
- **Start price** — derived from `change_pct`: `start = end / (1 + change_pct / 100)`.
- **Staleness check** — if the price timestamp is older than the threshold, the market is cancelled and all players refunded for that market.

### Step 3: Bitmap Flip

```rust
bitmap_store.flip(block_id)
```

Pending bitmaps merge into active. New submissions overwrite. No submission = keep the previous bitmap.

### Step 4: Per-Market Resolution

For each market:

1. Compute percent change from start to end price (integer basis points).
2. Apply resolution type + threshold to determine outcome: Up, Down, Flat, or Cancelled.
3. Decode each player's bitmap bit for this market index (1 = UP, 0 = DOWN).
4. Compute the flat stake: `deposit / num_markets` per market. Remainder is redistributed one extra unit to the first N markets.

### Step 5: Parimutuel Side Matching

Parimutuel = winners split the losers' pool. No house, no fixed odds. For markets with a clear winner:

1. Split players into winners (correct side) and losers (wrong side).
2. `matched = min(winner_total, loser_total)`.
3. Winners receive their matched stake back, plus a proportional share of the losers' matched pool.
4. Losers forfeit their matched stake; unmatched excess is refunded.
5. Edge cases — all same side, all losers, flat, cancelled — all produce full refunds.

```
Example: UP pool = 300 USDC, DOWN pool = 100 USDC, outcome = UP

matched = min(300, 100) = 100
Winners share 200 (their 100 back + losers' 100)
Losers receive 0
Unmatched UP excess (200) refunded to UP players proportionally
```

Total payout always equals total deposits. No USDC is created or destroyed.

### Step 6: Aggregate Settlement

```rust
compute_settlement(&tick_result, &player_deposits) → RoundSettlement
```

Per-player payouts and refunds are summed across all markets. Players are sorted by address ascending — a contract requirement. The result:

```rust
RoundSettlement {
    block_id: u64,
    players: Vec<Address>,      // sorted ascending
    payouts: Vec<U256>,         // 18-decimal L3 USDC
    deposits: Vec<U256>,        // per-player original deposit
    correct_counts: Vec<u32>,   // markets predicted correctly
    total_markets: u32,
}
```

Every oracle computes this independently. Same config, same prices, same bitmaps, same integer arithmetic — the results must be identical. If they are not, nothing settles.

## Phase 7: BLS Settlement Signing

Each oracle signs the settlement independently and contributes to a shared aggregation in Postgres.

### Per-Oracle Process

1. **Compute the deterministic message hash:**
   ```
   payouts_hash = keccak256(abi.encode(players[], payouts[]))
   message_hash = keccak256(abi.encode(
       chainId,
       visionAddress,
       "SETTLE_BLOCK",
       blockId,
       payoutsHash
   ))
   ```

2. **Sign** with the oracle's BLS private key.

3. **Shared DB aggregation** (`vision_settlement_proofs` table, `SELECT FOR UPDATE`):
   - First oracle to arrive: inserts `(block_id, players_hash, bls_sig, bitmap = 1 << node_index)`
   - Subsequent oracles: verify `players_hash` matches, aggregate the BLS signature, update the signer bitmap

4. **Check quorum.** When `popcount(bitmap) >= threshold` and the block has not yet been submitted:
   - Execute `settleBlock` on-chain
   - Mark `submitted = true`

The `players_hash` check is a guard against divergence. If two oracles compute different payouts — different prices, different bitmap sets, different resolution — their hashes will not match. The second oracle skips signing rather than corrupt the aggregated signature.

---

## Phase 8: On-Chain Settlement

The oracle with quorum calls:

```solidity
vision.settleBlock(
    blockId,
    players[],       // sorted ascending by address
    payouts[],       // 18-decimal USDC
    blsSignature,
    referenceNonce,
    signersBitmask
)
```

The contract validates:
- BLS signature against the aggregated public key in `OracleRegistry`
- Solvency: `sum(payouts) <= sum(deposits)`
- Player array is strictly ascending by address
- Block has not already been settled

On success:
- 0.05% protocol fee deducted from **profit only** (not from deposits)
- USDC transferred directly to each player's wallet
- `PlayerSettled` event emitted per player
- `BlockSettled` event emitted for the block
- `block.settled = true` — prevents double settlement

---

## Phase 9: Settlement Feedback

After resolution, the oracle sends outcomes back to the data-node:

```
POST /blocks/settlement
```

```json
{
  "source_id": "crypto",
  "asset_id": "bitcoin",
  "config_hash": "0x...",
  "start_price": "45000.5",
  "end_price": "45750.25",
  "change_pct": "1.67"
}
```

These records land in the `block_settlements` table. The next `BlockEngine` cycle (within 60s) reads the median of accumulated settlements and recalibrates thresholds for the next block.

Outcomes inform future thresholds. The system learns what 50/50 means for each asset from observed history, on a 60-second loop.

## Key Invariants

| Property | Guarantee |
|----------|-----------|
| **Determinism** | All oracles compute identical results — same config, same prices, same bitmaps, same integer math |
| **Zero-sum** | Total payouts = total deposits. No USDC created or destroyed |
| **BLS threshold** | `ceil(2n/3)` signatures required for every state-changing operation |
| **Solvency** | Contract rejects any settlement where `sum(payouts) > sum(deposits)` |
| **Idempotency** | `block.settled` flag prevents double settlement |
| **Config integrity** | Per-bitmap `config_hash` ensures market-order consistency across config updates |
| **Player sorting** | `settleBlock` requires strictly ascending addresses — contract enforced |
| **Self-calibrating** | Threshold feedback loop drives outcomes toward 50/50 over time |

## Database Persistence

### Data Node

| Table | Content | Retention |
|-------|---------|-----------|
| `market_prices` | Complete price history | 365 days |
| `market_prices_latest` | Live snapshot per (source, asset) | Current state |
| `block_configs` | Recommended configs | Signed: forever. Unsigned: 2 hours |
| `signed_block_configs` | BLS-signed configs (source, hash, sig, nonce) | Forever |
| `block_settlements` | Actual outcomes per (source, asset) | Forever |

### Oracle

| Table | Content | Retention |
|-------|---------|-----------|
| `vision_blocks` | Block metadata (id, source, config, state) | Forever |
| `vision_positions` | Player deposits per block | Forever |
| `vision_block_lifecycle` | Intent + timing (start, end, deadline) | Forever |
| `vision_round_players` | Per-player settlement results | Forever |
| `vision_settlement_proofs` | BLS aggregation state (hash, sig, bitmap, submitted) | Forever |
| `vision_bitmaps` | Bitmap storage (block, player, bytes, hash) | Forever |

On crash recovery, the oracle loads all non-settled blocks and all positions with balance > 0 from these tables. In-memory state rebuilds from Postgres.
