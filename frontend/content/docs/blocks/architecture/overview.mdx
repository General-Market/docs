# Architecture

Vision splits the prediction-market stack into five layers. No single component controls outcomes.

- **External data** — 98 APIs polled independently.
- **Data pipeline** — four data-node instances (three per-oracle, one read-only).
- **BLS consensus** — three oracles, threshold = `ceil(2n/3)` = 2.
- **L3 blockchain** — three contracts on Arbitrum Orbit (Vision, VisionReserve, OracleRegistry).
- **Frontend** — read-only, no signing authority.

**BLS** = Boneh-Lynn-Shacham signatures. They aggregate: many oracle signatures collapse into one for on-chain verification.

## Data Node Independence

Each oracle runs its own data-node. The three instances poll the same 98 APIs, store their own copies, compute their own snapshots. If one fails, the other two still reach consensus. If all three disagree on a price, the tick does not resolve.

A fourth read-only data-node serves the frontend and bot APIs. It holds no signing authority and cannot influence resolution.

<Info>
  A single compromised data source cannot alter outcomes. Each oracle computes prices from its own database, and BLS consensus rejects disagreement.
</Info>

## Contract Architecture

Three contracts, strict separation. The money sits in one. The logic lives in another. The keys live in a third.

<Frame>
  <img src="/images/vision/contracts.svg" alt="L3 contract architecture — Vision.sol for block logic, VisionReserve for USDC custody, OracleRegistry for BLS key management" />
</Frame>

<Warning>
  `VisionReserve` is the only contract that holds USDC. `Vision.sol` cannot move funds directly — it calls the reserve, which verifies the caller. A bug in block logic therefore cannot drain the treasury.
</Warning>

## BLS Consensus Model

Every state-changing action requires an aggregated BLS signature from a quorum of oracles: tick resolution, config updates, balance proofs, block creation. Threshold = `ceil(2n/3)`. With three oracles, two must agree. One dissenter blocks nothing. Two dissenters block everything.

## Source Modules

| Module | Responsibility |
|---|---|
| **Vision.sol** | Block registry, bitmap commits, config hashes, claim verification |
| **VisionReserve.sol** | USDC custody — deposits, withdrawals, reward transfers |
| **OracleRegistry.sol** | BLS public key management, aggregated pubkey, threshold |
| **Tick Engine** | Per-block tick scheduling, resolution, bitmap flip |
| **Resolver** | Price comparison, parimutuel matching, PnL computation |
| **Config Orchestrator** | Data-node polling, config proposals, BLS consensus on updates |
| **Chain Listener** | L3 event monitoring — new blocks, bitmap updates, deposits |
| **Bitmap Store** | Two-slot (pending/active) bitmap management per player per block |
| **BLS Signer** | Private key operations, signature aggregation |
| **Data Node** | 98-source collection, PostgreSQL storage, REST + WS + SSE serving |

<Info>
  Each oracle is co-located with its own data-node process. They share a VPS but not a database. The frontend data-node is a separate read-only instance serving public API traffic, isolated from oracle data pipelines.
</Info>
