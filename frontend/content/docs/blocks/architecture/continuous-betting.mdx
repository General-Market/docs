# Continuous Betting

You bet on tick N+1 during tick N. Your bet is committed before the prices that resolve it are known. That gap is what makes the market unexploitable.

- **Tick** — one resolution cycle. Duration set per source (60s to 30 days).
- **Bitmap** — packed bytes, one bit per market (1 = UP, 0 = DOWN).
- **Parimutuel** — winners split the losers' pool, no house edge.
- **BLS** — Boneh-Lynn-Shacham signatures, aggregable across oracles.

You do not pay to sit out. Absence is free; only an active bitmap is at risk.

## Two-Slot Bitmap Model

Each player has two bitmap slots per block. One is being resolved. One is being written to. They swap at every tick boundary.

<Frame>
  <img src="/images/vision/two-slot-bitmap.svg" alt="Two-slot bitmap engine — pending slot for next tick, active slot resolving now, with config-safe decoding using stored config_hash" />
</Frame>

<Warning>
  Each bitmap stores the `config_hash` it was submitted under. Without that, a config update between submission and resolution could decode bit 0 as `BTC-USD` when the player meant `ETH-USD`. The hash is the key that decodes the bitmap correctly.
</Warning>

## Commit-Reveal Scheme

No one sees your bets before you commit them on-chain. You commit `keccak256(bitmap)` first, then reveal the raw bytes to the oracles.

<Frame>
  <img src="/images/vision/commit-reveal.svg" alt="Commit-reveal flow — player commits keccak256 hash on-chain, reveals bitmap bytes to oracles, hash verification prevents tampering" />
</Frame>

Two reveal patterns exist:

- **Frontend** — reveal immediately after commit. Simpler UX. The hash locks the commitment, so security is identical.
- **Bots** — reveal near the tick boundary. Other participants cannot see positions until the last moment.

Both are equally secure. Late reveal is a privacy optimization, not a stronger guarantee.

## Tick Resolution

When a tick ends, oracles fetch real prices, compare them to player bitmaps, compute payouts, and sign the result. The pipeline is deterministic — three oracles must reach the same answer or nothing settles.

<Frame>
  <img src="/images/vision/resolution.svg" alt="Resolution pipeline — three oracles independently fetch prices, decode bitmaps, run parimutuel matching, BLS sign, then aggregate at tick boundary" />
</Frame>

### Parimutuel Settlement

Winners split the losers' stakes. No house, no fixed odds. The pool is all stake submitted for the tick:

| Element | Detail |
|---|---|
| **Pool** | Sum of all active players' `stakePerTick` |
| **Winners** | Players with more correct predictions than the threshold |
| **Losers** | Players below the threshold — their stakes fund the winners |
| **Distribution** | Winners receive proportional to their correct-market count |
| **Fee** | 0.05% on profits only — losers pay nothing extra |
| **Weighting** | Flat. No multiplier. Pure prediction accuracy determines payout |

## Config Orchestration

The config orchestrator runs every tick. It polls the data-node for recommendations and proposes updates through BLS consensus. A new data source becomes a live market without human intervention or a frontend deploy.

### Safeguards

| Safeguard | Value | Purpose |
|---|---|---|
| **MAX_BLOCKES** | 200 | On-chain cap prevents unbounded block flooding |
| **Rate limit** | 3 per hour | Prevents gas exhaustion from rapid auto-creation |
| **Min healthy assets** | 5 | Only creates blocks with sufficient live data |
| **Follower verification** | 20% threshold tolerance | Prevents compromised leader from crafting adversarial configs |
| **Config/bitmap decoupling** | Per-bitmap config_hash | Config updates never scramble active bitmaps |

## Dynamic Source Registry

The frontend hardcodes no source data. Every name, logo, category, and prefix comes from the data-node API. One endpoint is the entire contract between backend and frontend.

| Removed | Replaced by |
|---|---|
| `sources.ts` (VISION_SOURCES) | `GET /sources/registry` |
| `source-categories.ts` | API categories field |
| `market-categories.ts` (PREFIX_MAP) | API prefixes field |
| `VisionMarketsGrid` CATEGORY_GROUPS | API categories + order |
| `vision-blocks.json` (frontend) | `GET /blocks/signed` |
| Multiplier math (oracle) | Flat stakePerTick |
| Lock window logic | `lockOffset = 0` |
| `multiplier.rs` (entire file) | Deleted |
| Manual block registration | `BlockCreated` auto-detect |

<Info>
  Adding a new source = data-node config only. No frontend deploy needed. The `useSourceRegistry()` hook uses SWR with 5-minute revalidation; source metadata rarely changes. Stale-while-revalidate keeps the grid from flashing empty.
</Info>

## Tick Scheduling

Each config defines the next tick's duration. The data-node sets pacing per source: shorter ticks for fast-moving markets, longer for slow ones. Changes apply at the next tick boundary, never mid-tick.

```
next_settlement_time = tick_start_time + tickDuration
```

When a new config is promoted at a tick boundary:
1. Current tick resolves using the **old** config's duration
2. New config activates (lazy promotion)
3. Next tick starts with the **new** `tickDuration`
4. Settlement for the new tick = `now + new_tickDuration`

Config promotion happens **after** the bitmap flip. Active bitmaps always decode with their stored config. Config updates only affect bitmaps submitted after promotion.

## Cross-Oracle Bitmap Gossip

Before resolution, oracles verify they agree on the active player set. If one oracle missed a reveal, it requests the missing bitmap from peers. Resolution only proceeds on the intersection confirmed by all oracles.

The BLS consensus message includes `bitmap_set_hash = keccak256(sorted list of (player, bitmap_hash) pairs)`. All oracles must produce the same hash. If they diverge, the tick is skipped and no PnL is applied.

## Fund Safety

The contract holds the money. Oracles compute the outcomes. Every interaction crosses a verification boundary.

<Frame>
  <img src="/images/vision/security-boundaries.svg" alt="Fund safety matrix — player controls, oracle controls, and what oracles cannot do" />
</Frame>

| Layer | Protection | Attack prevented |
|---|---|---|
| **Deposits** | On-chain, player wallet tx | Oracles can't deposit/withdraw for you |
| **Bitmap commit** | On-chain keccak256 hash | Oracles can't change your bets |
| **Bitmap reveal** | Hash verification | Player can't change bets after commit |
| **Tick resolution** | BLS consensus (2/3+) | Single oracle can't manipulate outcomes |
| **Payouts** | BLS-signed proof on-chain | Fake payouts rejected by contract |
| **Withdrawals** | On-chain, player wallet tx | Only player can withdraw their funds |
| **Block config** | configHash on-chain | Config data verifiable against on-chain hash |
| **Sit-out** | No active bitmap = no risk | Absence is safe |

<Warning>
  Exception worth stating out loud: at the 2-of-3 BLS threshold, two colluding oracles can selectively exclude players from resolution. The `bitmap_set_hash` in BLS messages makes the exclusion auditable — anyone can compare the signed set against on-chain committed hashes. The attack is detectable on-chain.
</Warning>
