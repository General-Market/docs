# Glossary

Terms used across Vision contracts, oracles, and the frontend.

<dl>

### Balance Proof

A BLS-signed message from the oracle network attesting to a player's current USDC balance in a block. Required for `claimRewards` and `withdraw`. Fetched via `GET /vision/balance/{blockId}/{player}` and verified on-chain before the balance updates.

### Block

A group of markets that share one pool, tick duration, and resolution config. Created via `createBlock` with market IDs, resolution types, tick duration, and optional custom thresholds. Players join by depositing USDC and submitting bitmap commitments. Block IDs are sequential integers from 0.

### Block Metadata

Optional descriptive fields a block creator attaches: name (max 64 bytes), description (max 280 bytes), website URL (max 128 bytes), video URL (max 256 bytes), image URL (max 256 bytes). Written via `setBlockMetadata`, read via `getBlockMetadata`.

### Bitmap

A packed binary record of a player's bets across all markets in a block. One bit per market: `1` = UP (price increases), `0` = DOWN (price decreases or stays flat). Big-endian bit order. Committed on-chain as a `keccak256` hash and revealed to oracle nodes at resolution.

### BLS Signature

A Boneh-Lynn-Shacham cryptographic signature used for oracle consensus. Multiple oracle signatures aggregate into one, verified on-chain against the aggregated public key in the OracleRegistry. Required for `claimRewards`, `withdraw`, `pause`, `unpause`, `updateBlockMarkets`, and `forceWithdraw`.

### Bot Registry

An on-chain registry where automated trading bots publish an endpoint URL and public key hash. Registration is free, no collateral required. Oracle nodes discover registered bots via `getAllActiveBots()`. One bot per address.

### Commitment Multiplier

A logarithmic bonus on a player's effective stake based on how many ticks they commit to at join. Longer commitments earn a higher multiplier and a larger share of the winning pool. Rewards sustained participation and deeper liquidity.

### Commitment Offset

The gap between when a player commits their bitmap hash on-chain and when the tick begins. The commitment must land before tick start so the sealed hash is immutable through resolution. Blocks front-running based on early in-tick price movement.

### Custom Threshold

A user-defined basis point value used by resolution types ending in `_X` (UP_X, DOWN_X, FLAT_X). Sets how far the price must move to resolve UP or DOWN instead of FLAT. Provided per market in the `customThresholds` array at `createBlock`. 1 basis point = 0.01%.

### Data Node

The Rust backend that serves market prices for tick resolution. Aggregates 90+ external sources (CoinGecko, USGS, TFL, Deutsche Bahn, others) behind one API. Oracle nodes query it at the end of each tick to fetch closing prices for every market in every active block.

### Deployer Name

A human-readable name a block creator assigns to their address via `setDeployerName`. The frontend displays it beside every block that address created. Max 64 bytes.

### Early Multiplier

A bonus on a player's effective stake for committing the bitmap well before the tick deadline. The earlier the commitment, the higher the multiplier. Rewards decisive action and discourages last-second sniping.

### Fee Collector

The address authorized to call `collectFees()` and withdraw accumulated protocol fees. Set at deployment as an immutable reference. Only this address can drain the fee accumulator.

### Market ID

A source-prefix + asset-name identifier that uniquely names a market. `crypto_btc` is Bitcoin from the crypto source; `usgs_earthquake` is earthquake data from USGS. Used in block creation, data-node queries, and frontend routing.

### Market Outcome

The resolved result of one market in one tick. Three possible outcomes: **UP** (price exceeded the threshold), **DOWN** (price fell below the negative threshold), **FLAT** (price stayed inside the threshold range). Compared against each player's bitmap bit for that market to determine winners and losers.

### Parimutuel

Vision's betting model. All stakes in a tick pool together; winners split the losers' stakes in proportion to their `stakePerTick`. No counterparty, no market maker. The protocol is zero-sum minus a 0.05% fee on profits. Each winner's share equals their stake divided by total winning stake.

### Points

Season 1 rewards earned by providing liquidity in blocks. Accrue from stake, commitment duration, and cross-block activity. A measure of protocol participation that may convert to future rewards.

### Resolution Type

A per-market parameter that fixes the price-movement threshold used to resolve the outcome. 14 types: UP_0 (any increase), UP_30 (≥ 0.30%), UP_X (≥ custom), DOWN_0 (any decrease), DOWN_30 (≥ 0.30%), DOWN_X (≥ custom), FLAT_0 (no change), FLAT_X (within custom range), UP_300 (≥ 3%), UP_3000 (≥ 30%), DOWN_300 (≥ 3% decrease), DOWN_3000 (≥ 30% decrease), FLAT_300 (within 3%), FLAT_3000 (within 30%). Types 0–7 are standard; 8–13 are hardcoded presets. See [Resolution Types](/docs/blocks/concepts/resolution-types) for the full reference.

### Reveal Window

The period after tick end in which players must reveal their bitmap bytes to oracle nodes. Oracles verify the revealed bitmap against the on-chain `keccak256` hash. Miss the window and the bitmap is treated as all-zeros (all DOWN) for that tick.

### Sealed Commitment

A `keccak256` hash of a player's bitmap submitted on-chain before the bitmap bytes are revealed. Blocks front-running — other players cannot see bet directions until after the commitment deadline. Oracle nodes verify the revealed bitmap matches the on-chain hash stored in `PlayerPosition.bitmapHash`.

### Source

An external data provider that feeds market prices into Vision via the data node. Examples: CoinGecko (crypto), USGS (earthquakes), TFL (London transport), Deutsche Bahn (German rail) and 90+ others. Each source carries a unique prefix (`crypto`, `usgs`, `tfl`) used in market IDs. Source config lives in `data-node/src/config/`.

### Stake Per Tick

The USDC amount (6 decimals) a player wagers each tick. Set at `joinBlock`, immutable for the life of the position. Minimum: 0.1 USDC (`100000` raw). Each tick the balance falls by `stakePerTick` and rises by the player's share of the winning pool when predictions hit.

### Tick

A single resolution interval inside a block. At each tick end, oracle nodes fetch closing prices, resolve every market to a binary outcome, compare each bitmap against outcomes, and distribute the pool to winners. Tick durations run from 1 second to 30 days and are immutable once the block is created. Computed as `block.timestamp / tickDuration`.

### Tick Duration

The fixed interval between resolution cycles, set at block creation and immutable. Range: 60 seconds to 30 days. Short ticks (60 s, 5 min) suit high-frequency trading; long ticks (1 day, 7 days) suit macro bets. Sets how often prices sample and the pool redistributes.

### TVL (Total Value Locked)

The total USDC across all active player positions in a block, or across all blocks. The aggregate capital at risk in the parimutuel pool. Rises on deposits, falls on withdrawals and claims.

### Vision

The sealed parimutuel prediction market on Arbitrum. Traders bet whether asset prices move UP or DOWN over fixed ticks. Every bet inside a tick shares one pool — winners split losers' stakes, minus a 0.05% protocol fee on profits. The contract is `Vision.sol`; some code paths use the internal name "P2Pool".

</dl>
