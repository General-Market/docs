Change a DTF's asset weights without changing the NAV (Net Asset Value — portfolio value per share). ~3 min from clicking Rebalance to oracle settlement.

**Prereqs:**
- You are the deployer of the DTF (only the deployer can rebalance).
- Your wallet is on the Settlement chain — see [Settlement](/index/guides/settlement).
- A target weight set that sums to exactly 100%, with each asset ≥ 0.25%.

**What it does:** recomputes per-share asset quantities so the basket matches new target weights. NAV per share is preserved exactly; only exposure changes.

## What Is Rebalancing?

Rebalancing recalculates per-share quantities so the basket matches new target weights. The invariant: **NAV per share does not change**. Exposure shifts; value per share stays exactly where it was.

```text
 ┌─────────────────────────────────────────────────────────────────────┐
 │                     REBALANCING IN ONE PICTURE                     │
 │                                                                    │
 │   BEFORE                                    AFTER                  │
 │   ┌──────────────────────┐                  ┌──────────────────────┐│
 │   │ Asset  Wt     Qty    │                  │ Asset  Wt     Qty    ││
 │   │ ───── ─────  ─────── │   updateWeights  │ ───── ─────  ─────── ││
 │   │ BTC   33%   0.000007 │ ────────────────►│ BTC   50%   0.000010 ││
 │   │ ETH   33%   0.000111 │                  │ ETH   30%   0.000102 ││
 │   │ SOL   34%   0.003334 │                  │ SOL   20%   0.001982 ││
 │   │                      │                  │                      ││
 │   │ NAV = $1.19          │                  │ NAV = $1.19          ││
 │   └──────────────────────┘                  └──────────────────────┘│
 │                                                                    │
 │              Weights change. Quantities change. NAV stays.         │
 └─────────────────────────────────────────────────────────────────────┘
```

Quantities are the only state stored on-chain (in `_itpInventory`). Buys and sells mint or burn shares proportionally — they never touch quantities. Only a rebalance does.

## Why Rebalance?

Prices move. The dollar weight of each asset drifts from its target. After enough drift, the DTF no longer matches the thesis you deployed.

```text
  CREATION (all prices = $1)           6 MONTHS LATER
  ┌────────────────────────┐           ┌────────────────────────┐
  │ Target   Effective     │           │ Target   Effective     │
  │ Weight   Weight        │           │ Weight   Weight        │
  │ ──────   ─────────     │           │ ──────   ─────────     │
  │ BTC 50%  ████████ 50%  │           │ BTC 50%  ██████████ 62%│
  │ ETH 30%  █████    30%  │           │ ETH 30%  ████      25% │
  │ SOL 20%  ████     20%  │           │ SOL 20%  ██        13% │
  └────────────────────────┘           └────────────────────────┘
                                        BTC outperformed → its
                                        effective weight grew.
                                        The ITP no longer matches
                                        the deployer's thesis.
```

Four reasons to rebalance:

- **Weight drift** — prices moved enough that effective weights diverge from targets.
- **Thesis change** — you want more exposure to one sector and less to another.
- **Asset rotation** — remove a delisted or underperforming token, add a new one.
- **Scheduled discipline** — some deployers rebalance on a fixed cadence (monthly, quarterly) to avoid discretionary timing.

## The Rebalance Formula

The core formula recalculates quantities from the new weights and the current NAV:

```text
  ┌─────────────────────────────────────────────────┐
  │                                                 │
  │   qty_new[i] = (w_new[i] * currentNAV)          │
  │                ─────────────────────────         │
  │                      price[i]                    │
  │                                                 │
  │   where:                                        │
  │     w_new[i]    = new target weight (sums to 1) │
  │     currentNAV  = NAV at moment of rebalance    │
  │     price[i]    = current price of asset i      │
  │                                                 │
  └─────────────────────────────────────────────────┘
```

The formula is identical to the one used at creation, except `currentNAV` replaces the initial `1e18` ($1.00). New quantities × current prices × summed = same NAV. The arithmetic guarantees preservation.

## NAV Preservation: Worked Example

A three-asset DTF, before and after a rebalance. NAV stays constant within rounding precision.

### Setup

A DTF was created with three assets at equal weight. Prices have since moved:

```text
  ┌──────────────────────────────────────────────────────────┐
  │ CURRENT STATE (before rebalance)                         │
  │                                                          │
  │ Asset   Price       Qty/Share       Dollar Value         │
  │ ─────   ─────────   ─────────────   ────────────         │
  │ BTC     $60,000     0.000006666     $0.3999              │
  │ ETH     $3,500      0.000111100     $0.3889              │
  │ SOL     $120        0.003334000     $0.4001              │
  │                                     ────────             │
  │                              NAV =  $1.1889              │
  └──────────────────────────────────────────────────────────┘
```

### Rebalance to New Weights

The deployer changes weights to BTC 50%, ETH 30%, SOL 20%:

```text
  ┌──────────────────────────────────────────────────────────┐
  │ COMPUTING NEW QUANTITIES                                 │
  │                                                          │
  │ qty_new[BTC] = (0.50 * 1.1889) / 60000 = 0.000009908    │
  │ qty_new[ETH] = (0.30 * 1.1889) / 3500  = 0.000101906    │
  │ qty_new[SOL] = (0.20 * 1.1889) / 120   = 0.001981500    │
  └──────────────────────────────────────────────────────────┘
```

### Verification: NAV After Rebalance

```text
  ┌──────────────────────────────────────────────────────────┐
  │ POST-REBALANCE NAV CHECK                                 │
  │                                                          │
  │ Asset   Price       New Qty         Dollar Value         │
  │ ─────   ─────────   ─────────────   ────────────         │
  │ BTC     $60,000     0.000009908     $0.5945              │
  │ ETH     $3,500      0.000101906     $0.3567              │
  │ SOL     $120        0.001981500     $0.2378              │
  │                                     ────────             │
  │                              NAV =  $1.1890              │
  │                                                          │
  │         Before: $1.1889  |  After: $1.1890               │
  │         Difference: $0.0001 (rounding only)              │
  └──────────────────────────────────────────────────────────┘
```

NAV preserved within rounding precision. Each share holds the same dollar value before and after the rebalance — only exposure shifts.

  ETH ████████████  32.7%             ETH ███████████        30.0%
  SOL ████████████  33.7%             SOL ███████            20.0%
       ▲                                   ▲

## Rebalancing Step-by-Step (UI)

Six steps. ~3 min from clicking Rebalance to AP settlement starting.

<Steps>
  <Step title="Step 1: Open the rebalance modal">
    Open the DTF's detail page. If you are the deployer, the **Rebalance** button appears in the management section. Click it.

    <Note>
    Only the deployer's wallet can initiate a rebalance. The button does not appear for other users.
    </Note>
  </Step>

  <Step title="Step 2: Adjust weights">
    The modal lists every current asset with its weight. Edit the percentages. Weights must sum to exactly **100%** — the contract rejects any other total.

    ```text
     ┌─────────────────────────────────────────────┐
     │  Rebalance: DeFi Blue Chips                 │
     │                                              │
     │  Asset        Current    New                 │
     │  ─────        ───────    ───                 │
     │  BTC          33.3%      [ 50.0% ]           │
     │  ETH          33.3%      [ 30.0% ]           │
     │  SOL          33.4%      [ 20.0% ]           │
     │                                              │
     │  Total: 100.0%              [Rebalance]      │
     └─────────────────────────────────────────────┘
    ```
  </Step>

  <Step title="Step 3: Add or remove assets (optional)">
    Use the search bar to add new assets. To remove one, set its weight to 0% or click remove.

    Add and remove are supported in the same rebalance — one transaction handles all changes.
  </Step>

  <Step title="Step 4: Submit the request">
    Click **Rebalance**. The wallet prompts for a transaction on the Settlement chain.

    What this does: calls `requestRebalance` on the BridgeProxy, which emits a `RebalanceRequested` event. Oracles pick up the event automatically.

    ```text
     ┌──────────────────────────────────────────────────────────┐
     │                  REBALANCE PIPELINE                      │
     │                                                          │
     │  Deployer                                                │
     │    │                                                     │
     │    ▼                                                     │
     │  requestRebalance()  ─── Settlement chain (MetaMask tx)  │
     │    │                                                     │
     │    ▼                                                     │
     │  RebalanceRequested event emitted                        │
     │    │                                                     │
     │    ▼                                                     │
     │  Oracle nodes detect the event                           │
     │    │                                                     │
     │    ▼                                                     │
     │  Oracles verify weights + fetch prices                   │
     │    │                                                     │
     │    ▼                                                     │
     │  BLS consensus among oracles                             │
     │    │                                                     │
     │    ▼                                                     │
     │  rebalance() called on L3 (with BLS signature)           │
     │    │                                                     │
     │    ▼                                                     │
     │  On-chain: new quantities computed + stored              │
     │    │                                                     │
     │    ▼                                                     │
     │  AssetTradeRequest events emitted for each delta         │
     │    │                                                     │
     │    ▼                                                     │
     │  AP executes trades to match new inventory               │
     │                                                          │
     └──────────────────────────────────────────────────────────┘
    ```
  </Step>

  <Step title="Step 5: Wait for oracle execution">
    Oracle nodes detect the event, validate the new weights, fetch current prices, and reach BLS (Boneless–Lynn–Shacham — a multi-signature consensus scheme) consensus. ~1–2 min.

    Once consensus is reached, the oracles call `rebalance()` on L3 with the aggregated BLS signature. The on-chain function does seven things in order:
    1. Snapshots old inventory.
    2. Removes assets (if any indices specified).
    3. Adds new assets (if any addresses specified).
    4. Validates weights sum to 100% and each weight ≥ 0.25%.
    5. Computes new quantities: `qty[i] = (weight[i] * NAV) / price[i]`.
    6. Emits a `Rebalanced` event with final state.
    7. Emits `AssetTradeRequest` events for each inventory delta.
  </Step>

  <Step title="Step 6: AP settles trades">
    The AP (Authorized Participant — the off-chain fill agent) reads `AssetTradeRequest` events and executes trades on exchanges to align physical holdings with the new quantities.

    - Assets with increased quantities → bought.
    - Assets with decreased quantities → sold.
    - Settlement time varies with delta size and asset liquidity.
  </Step>
</Steps>

## On-Chain Mechanics

The rebalance logic lives in `RebalanceLib.sol`, called via `delegatecall` from `Investment`. Eight steps run atomically:

```text
  ┌──────────────────────────────────────────────────────────┐
  │                 RebalanceLib.rebalance()                  │
  │                                                          │
  │  Step 1:  Read current NAV from _itpNavs[itpId]          │
  │                                                          │
  │  Step 2:  Snapshot old assets + inventory (for deltas)   │
  │                                                          │
  │  Step 3:  Swap-and-pop removed assets (descending order) │
  │           ┌─────────────────────────────────────┐        │
  │           │ assets:  [A, B, C, D, E]            │        │
  │           │ remove:  [3, 1]  (D, then B)        │        │
  │           │                                     │        │
  │           │ remove idx 3: swap D↔E, pop         │        │
  │           │   → [A, B, C, E]                    │        │
  │           │ remove idx 1: swap B↔E, pop         │        │
  │           │   → [A, E, C]                       │        │
  │           └─────────────────────────────────────┘        │
  │                                                          │
  │  Step 4:  Push new assets to end of arrays               │
  │                                                          │
  │  Step 5:  Validate weights (sum = 1e18, each >= 0.25%)   │
  │                                                          │
  │  Step 6:  Compute new inventory for ALL assets           │
  │           inventory[i] = (newWeights[i] * nav) / price[i]│
  │                                                          │
  │  Step 7:  Update metadata, write NAV (preserved)         │
  │                                                          │
  │  Step 8:  Emit Rebalanced + AssetTradeRequest events     │
  └──────────────────────────────────────────────────────────┘
```

### Asset trade deltas

After computing new quantities, the contract compares old vs. new inventory and emits one `AssetTradeRequest` event per asset. The delta tells the AP what to buy and what to sell.

```text
  Asset   Old Qty       New Qty       Delta         Action
  ─────   ──────────    ──────────    ──────────    ──────
  BTC     0.000006666   0.000009908   +0.000003242  BUY
  ETH     0.000111100   0.000101906   -0.000009194  SELL
  SOL     0.003334000   0.001981500   -0.001352500  SELL
```

The AP executes these deltas on exchanges. Physical backing is brought back in line with on-chain inventory.

## Who Can Rebalance?

```text
  ┌─────────────────────────────────────────────────┐
  │                                                 │
  │  requestRebalance()     Anyone can call          │
  │        │                (permissionless)         │
  │        ▼                                        │
  │  Oracle verification    Oracles check that the  │
  │        │                caller is the ITP        │
  │        │                deployer before signing  │
  │        ▼                                        │
  │  rebalance()            Requires BLS consensus  │
  │                         (oracle nodes only)      │
  │                                                 │
  └─────────────────────────────────────────────────┘
```

`requestRebalance()` is technically permissionless — anyone can call it. The oracle nodes then verify the caller is the DTF's deployer before signing. Non-deployer calls fail at the oracle layer.

<Warning>
BLS signature verification is never bypassed — not in local dev, not in tests, not anywhere. Removing it would break the security model of the protocol.
</Warning>

## When to Rebalance

Four common strategies. Pick one based on how active you want to be.

| Strategy | Description | Typical cadence |
|----------|-------------|-----------------|
| **Threshold-based** | Rebalance when any asset's effective weight deviates by more than X% from target | Drift > 5–10% |
| **Calendar-based** | Rebalance on a fixed schedule regardless of drift | Monthly or quarterly |
| **Event-driven** | Rebalance in response to market events (delistings, new token launches, thesis changes) | As needed |
| **Hybrid** | Calendar-based with threshold overrides for large moves | Monthly + 10% drift trigger |

```text
  Weight drift over time (no rebalance)
  ──────────────────────────────────────
  65% ┤                               ╭── BTC effective weight
      │                          ╭───╯
  55% ┤                     ╭───╯
      │                ╭───╯
  50% ┤───────── target ────────────────────────────────────
      │           ╰───╮
  45% ┤                ╰───╮
      │                     ╰───╮         ETH + SOL drift
  35% ┤                          ╰───╮    down accordingly
      │                               ╰──
  25% ┤
      └──┬──────┬──────┬──────┬──────┬──
        M1     M2     M3     M4     M5
                                     ▲
                              rebalance here
                              (drift exceeded threshold)
```

## Costs of Rebalancing

Three cost categories. The trade-off: cost of rebalancing vs. cost of drifting away from the target.

| Cost | Description |
|------|-------------|
| **Gas** | The `requestRebalance()` transaction on Settlement costs gas. The `rebalance()` execution on L3 is paid by oracles. |
| **Trading fees** | The AP buys and sells assets to match the new inventory. Each trade incurs exchange fees and slippage. |
| **Spread/slippage** | Larger inventory deltas mean larger trades, which can move the market — especially for less liquid assets. |

```text
  ┌──────────────────────────────────────────────────────┐
  │              REBALANCE COST TRADEOFF                 │
  │                                                      │
  │  Rebalance     Too frequent           Too infrequent │
  │  Frequency     ────────────           ──────────────  │
  │                                                      │
  │  Gas costs     High (many txs)        Low             │
  │  Trade fees    High (many trades)     Low             │
  │  Weight drift  Low (stays on target)  High (drifts)   │
  │  Tracking err  Low                    High            │
  │                                                      │
  │  Sweet spot: rebalance when drift is meaningful      │
  │  but not so often that costs eat into returns.       │
  └──────────────────────────────────────────────────────┘
```

<Tip>
For most DTFs, rebalance when any asset drifts more than 5–10% from target weight. This balances precision against gas + trading costs.
</Tip>

## Constraints

The contract rejects any rebalance that violates one of the following:

- **Minimum weight**: each asset must have at least **0.25%** weight (25e14 in contract math).
- **Weight sum**: weights must sum to exactly **100%** (1e18).
- **No zero prices**: every asset must have a non-zero price at rebalance time.
- **No duplicate assets**: cannot add an asset that already exists in the basket.
- **Remove indices descending**: when removing multiple assets, indices must be sorted in descending order (the contract uses swap-and-pop).
- **DTF must be active**: cannot rebalance a paused or inactive DTF.
