# Index L3 Chain

The Index L3 is a dedicated Arbitrum Orbit chain ("L3" = Layer 3, a rollup that posts data to another rollup) built to host the Index protocol and nothing else.

It exists for five reasons:

- Dedicated block space — no congestion from unrelated apps.
- Sub-second finality — required for the 1-second oracle consensus cycle.
- Near-zero gas — the team controls gas pricing.
- A 49,152-byte contract size limit (double the EVM default) so `Index.sol` fits in one contract.
- Native BN254 precompiles for on-chain BLS verification.

## Why a Dedicated Chain

### Dedicated Block Space

The L3 processes Index transactions only. No competing apps share the mempool, so an NFT mint elsewhere cannot displace a buy order or a Vision tick.

### Sub-Second Finality

Orders confirm inside one block. The oracle consensus cycle runs every 1 second. Sub-second finality is a hard requirement for real-time price feeds and Vision tick resolution, not an optimisation.

### Near-Zero Gas Costs

The team controls gas pricing. Fees prevent spam, not extract rent. A buy order, a Vision bet, or a bitmap submission each costs fractions of a cent.

### Custom Gas Token (GM)

GM is a custom ERC-20 that serves as the native gas currency on L3. It originates on the Settlement chain (Sonic Testnet) and is deposited to L3 through the `ERC20Inbox`. The team mints GM and distributes it through the faucet.

<Info>
The `native-token: 0x0000000000000000000000000000000000000000` convention in Orbit configuration means "custom ERC-20 gas token," not ETH. GM is that token.
</Info>

### Enlarged Contract Size Limit

The standard EVM contract size limit is 24,576 bytes. `Index.sol` — order management, DTF creation, NAV computation, BLS verification — does not fit. The L3 doubles the limit to 49,152 bytes so the contract ships as one unit instead of a proxy graph.

### BN254 Precompiles

The L3 exposes EVM precompiles for BN254 (alt-bn128) elliptic-curve operations: `ecAdd` at `0x06`, `ecMul` at `0x07`, `ecPairing` at `0x08`. These make on-chain verification of aggregated BLS signatures gas-cheap. Without them, every block confirmation would be prohibitive.

## What Lives on L3

The L3 hosts every contract on the hot path.

<L3ChainTopology />

- **Core protocol contracts** — `Index`, `Governance`, `OracleRegistry`. Order management, DTF creation, BLS key registration.
- **Vision prediction markets** — Block creation, player operations, tick resolution, bot registry.
- **DTF vaults** — One ERC-4626 vault per DTF.
- **Morpho lending markets** — Borrow USDC against DTF collateral. `ITPNAVOracle` feeds Morpho BLS-verified prices.
- **Bridge endpoints** — Custody contracts and proxy for cross-chain operations with Settlement.

## USDC on L3

<Warning>
USDC on Index L3 uses **18 decimals**, not the standard 6. All contract interactions, balance reads, and amount parameters use 18-decimal precision. 100 USDC = `100_000_000_000_000_000_000` (1e20). Always check which chain a value originates from before passing it to a contract.
</Warning>

## Architecture Characteristics

### Rollup Mode

The L3 runs as a rollup, not a Data Availability Committee (DAC). Transaction data is posted to the parent chain (Sonic Testnet), inheriting its security. The cost is higher data fees in exchange for stronger finality assurance.

### Cross-Chain Messages

Messages between L3 and Settlement use Arbitrum's retryable ticket system with a 7-day lifetime. A failed message can be retried within that window. The bridge contracts retry automatically for standard operations.

### Upgradeability

All protocol contracts use UUPS proxies (Universal Upgradeable Proxy Standard). The proxy address is permanent; only the implementation behind it changes. Users keep the same address across upgrades.

### Oracle Consensus

Three oracle nodes produce BLS-signed attestations every second. Price feeds, block confirmations, NAV updates, and Vision tick resolutions all flow through this consensus layer. The BN254 precompiles make on-chain verification of aggregated signatures gas-cheap.
