# Oracle Nodes

Three Rust services run the consensus layer. They batch pending orders into blocks, sign them with BLS partial signatures, aggregate, and submit the confirmed block to L3. One cycle per second.

The five obligations run every cycle:

- Collect pending orders from `Index.sol`.
- Propose a block and coordinate BLS partial-signature exchange.
- Submit the confirmed block on-chain with the aggregated signature.
- Trigger rebalancing when DTF weights are updated.
- Maintain price consensus for NAV computation.

The codebase is 68K LOC of Rust.

## Key Modules

| Module | Responsibility |
|---|---|
| **consensus/** | BLS signature aggregation, threshold validation, block agreement protocol |
| **cycle/** | 1-second cycle state machine with 5 phases (200ms each) |
| **p2p/** | TCP transport with TLS, peer discovery (static config + on-chain registry) |
| **chain/** | Ethereum/L3 RPC interaction, transaction submission, event monitoring |
| **netting/** | Order netting engine — matches opposing orders, handles USDT pair routing, computes net exposure |
| **leader/** | Round-robin leader election, block proposal construction |
| **price/** | Price feed aggregation from data node, consensus on prices used in blocks |
| **state/** | Local state management, pending order tracking, block history |

## Consensus Flow

Every block requires `ceil(2n/3)` aggregated BLS signatures before it can be confirmed on-chain.

## Cycle Timing

The 1-second cycle splits into five 200ms phases, each with one job.

| Phase | Duration | Action |
|---|---|---|
| **COLLECT** | 200ms | Gather new pending orders from chain events and peer gossip |
| **PROPOSE** | 200ms | Leader constructs and broadcasts the proposed block |
| **SIGN_SUBMIT** | 200ms | Peer oracle nodes validate the proposal and return BLS partial signatures |
| **CONFIRM** | 200ms | Leader aggregates signatures and submits the confirmed block on-chain |
| **REBALANCE** | 200ms | Process any pending DTF rebalance operations (weight updates → new quantities) |

## Leader Election

The leader rotates every cycle, round-robin, ordered by the node's index in `OracleRegistry.sol`. The current leader builds the proposal, aggregates partial signatures, and submits the block. A failed leader loses the cycle; the next leader takes over on the next tick.

## Peer-to-Peer Transport

| Property | Detail |
|---|---|
| **Transport** | TCP with TLS |
| **Discovery** | Static config + on-chain registry via `OracleRegistry.sol` |
| **Messages** | Block proposals, BLS partial signatures, heartbeats |
| **Serialization** | Binary format, minimises serialisation latency on the consensus path |

Connections to peers are persistent and reconnect automatically. The P2P layer handles network-level retries so the consensus layer does not.

## Netting Engine

A buyer and a seller of the same asset in the same block offset each other. Only the net delta is sent to the AP for execution on Bitget.

- **Order netting** — buy and sell on the same asset offset, reducing the AP's execution size.
- **USDT pair routing** — used when a direct asset/USDC pair is unavailable on Bitget.
- **Rebalance deltas** — on weight change, computes the minimal trade set to move from old to new quantities while preserving NAV.

## BLS Details

| Property | Detail |
|---|---|
| **Curve** | BN254 (alt_bn128) |
| **EVM compatibility** | Uses precompiles at `0x06` (addition), `0x07` (scalar multiplication), `0x08` (pairing) |
| **Key registration** | Each oracle node registers the node's BLS public key in `OracleRegistry.sol` |
| **Aggregation** | Partial signatures are aggregated into a single signature by the leader |
| **Verification** | On-chain via `BLSLib.sol` against the stored aggregated public key |

<Warning>
  BLS verification is **never bypassed** — not in local development, not in tests, not anywhere. If BLS is blocking development, fix the pipeline: generate proper test keys, register them in `OracleRegistry`, compute valid signatures.
</Warning>

## Security: AP Isolation (FR13)

Oracle nodes have no direct communication channel to the AP. The AP discovers confirmed blocks only through on-chain `TradeRequest` events.

<Warning>
  The boundary prevents collusion: if signers and the trade executor could coordinate off-chain, the system would have a single point of compromise.
</Warning>
