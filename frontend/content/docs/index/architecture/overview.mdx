# System Architecture

Eight services, two chains, twenty-nine contracts — vertically integrated from data ingestion to settlement.

Index runs Dex Traded Funds (DTFs — on-chain ETFs that rebalance per BLS-signed oracle prices) and parimutuel prediction markets on the same stack. Every state change passes through BLS consensus (a threshold signature scheme where `ceil(2n/3)` oracle nodes must agree before the chain accepts the block).

Key terms used throughout this page:

- **L3** — Index's Arbitrum Orbit chain (custom Layer 3, gas token GM, 18-decimal USDC).
- **Settlement** — Arbitrum (standard 6-decimal USDC), where DTF shares live as ERC-20s.
- **AP** — Authorized Participant. The keeper that executes asset trades on Bitget after the oracles confirm a block.
- **NAV** — Net Asset Value. The per-share value of a DTF, computed from fixed inventory and current prices.

## Component Summary

The protocol is built from eight services. Each has one job.

<CardGroup cols={2}>
  <Card title="Oracle Nodes (3x)" icon="server">
    Three Rust nodes run a 1-second consensus cycle. Round-robin leader, BLS partial signatures, `ceil(2n/3)` threshold. They block orders, sign them, and submit confirmed blocks on-chain.
  </Card>
  <Card title="AP / Keeper" icon="gears">
    Watches on-chain `TradeRequest` events, executes the matching trades on Bitget, confirms fills with BLS signatures. Also relays bridge operations. The AP has no direct channel to the oracles — see FR13 below.
  </Card>
  <Card title="Data Node" icon="database">
    90+ sources written to PostgreSQL — CoinGecko, Binance, earthquake feeds, train delays. REST + SSE on port 8200. Feeds NAV computation, backtesting, and every price the protocol uses.
  </Card>
  <Card title="Curator" icon="eye">
    Collects NAV from oracles, pushes it to the on-chain oracle, rebalances Morpho lending allocations, monitors health factors. Runs silently until a metric breaches threshold.
  </Card>
  <Card title="Next.js Frontend" icon="browser">
    The user surface: trading, prediction markets, explorer, points, learning content. Deployed on Vercel. Consumes Data Node APIs over SSE.
  </Card>
  <Card title="Vision Bot" icon="robot">
    Python strategy framework. Places automated bets on Vision blocks through the on-chain `BotRegistry`.
  </Card>
  <Card title="Social Bot" icon="twitter">
    Watches 98 real-world data sources for anomalies — transport delays, power outages, earthquakes — and posts them to Twitter/X.
  </Card>
  <Card title="Smart Contracts" icon="file-contract">
    29 Solidity contracts across two chains. UUPS proxies. BLS verification on every critical path. No test modes, no admin bypasses.
  </Card>
</CardGroup>

## Two Chains, One Protocol

The protocol runs on two chains because each one solves a problem the other cannot.

- **L3** owns the hot path: 1-second order blocking, Vision tick resolution, NAV oracle updates. Near-zero gas, fully controlled sequencer.
- **Settlement (Arbitrum)** owns composability: DTF shares as ERC-20, Morpho collateral, standard wallet UX.

<OverviewTwoChains />

<Warning>
  **L3 and Settlement use different USDC decimals.** L3 uses 18-decimal USDC. Settlement uses standard 6-decimal USDC. Always check which chain a value originates from before passing it to a contract call.
</Warning>

### Why Two Chains?

| Concern | L3 (Orbit) | Settlement (Arbitrum) |
|---|---|---|
| **Gas costs** | Near-zero (custom Orbit chain) | Standard Arbitrum fees |
| **Speed** | Sub-second finality | ~250ms Arbitrum finality |
| **Composability** | Limited (custom chain) | Full Arbitrum DeFi ecosystem |
| **User access** | Via frontend or bots | Direct wallet interaction |

L3 handles operations that must be cheap. Settlement handles operations that must be composable. DTF shares minted on L3 cross the bridge and become ERC-20 collateral inside Morpho lending markets. See [Bridge Architecture](/index/architecture/bridge) for the cross-chain flow.

## Order Lifecycle

A buy order passes through five steps before it becomes shares in a wallet. Each step verifies the one before it.

<OverviewOrderLifecycle />

<Warning>
  **Oracle-AP isolation (FR13):** Oracle nodes have no direct channel to the AP. The AP discovers confirmed blocks only through on-chain `TradeRequest` events. This boundary prevents collusion between consensus participants and the trade executor.
</Warning>

### Bridge Order Flow

A user submitting from Settlement instead of L3 routes through the bridge. The pipeline is the same; the entry point differs.

<OverviewBridgeOrderFlow />

<Tip>
  Bridged DTF shares on Arbitrum are standard ERC-20 tokens. They can be used as collateral in Morpho lending markets through `ITPNAVOracle`, which provides on-chain NAV pricing.

## Service Connectivity Map

Every service-to-service link uses a fixed protocol and a fixed purpose. The table below is the full list.

<OverviewConnectivityMap />

### Connection Types

| From | To | Protocol | Purpose |
|---|---|---|---|
| Frontend | Data Node | REST + SSE | Prices, NAV, portfolio, backtesting, streaming updates |
| Frontend | L3 Chain | JSON-RPC | Read contract state, submit user transactions |
| Frontend | Settlement | JSON-RPC | Bridge orders, read bridged DTF balances |
| Oracle Nodes | L3 Chain | JSON-RPC | Submit BLS-signed block confirmations |
| Oracle Nodes | Data Node | REST | Fetch latest prices for block pricing |
| Oracle Nodes | Oracle Nodes | TCP + TLS | P2P consensus messages, BLS partial signatures |
| AP / Keeper | L3 Chain | JSON-RPC (events) | Monitor `TradeRequest` events |
| AP / Keeper | Settlement | JSON-RPC | Execute `completeBuyOrder`, bridge operations |
| AP / Keeper | Bitget | REST API | Execute market orders, check balances |
| Curator | L3 Chain | JSON-RPC | Read NAV, publish oracle values |
| Curator | Morpho | JSON-RPC | Manage lending allocations |
| Vision Bot | Data Node | REST | Read market data for strategy signals |
| Vision Bot | L3 Chain | JSON-RPC | Place bets on Vision blocks |
| Social Bot | Data Node | REST | Read real-world data for anomaly detection |
| Social Bot | Twitter/X | API | Post detected anomalies |

## Technology Stack

Four languages, one per layer: Rust for the backend services, Solidity for the contracts, Python for the bots, TypeScript for the frontend.

<OverviewTechStack />

| Technology | Version / Detail |
|---|---|
| **Rust** | Tokio async runtime, ~68K LOC for all Rust services |
| **Solidity** | OpenZeppelin 5.x, Foundry toolchain, ~7.3K LOC |
| **Next.js** | App Router, deployed on Vercel |
| **Python** | Vision Bot strategy framework, Social Bot anomaly engine |
| **PostgreSQL** | Price history, portfolio snapshots, backtesting data |
| **BLS Cryptography** | BN254 curve, EVM precompiles (0x06, 0x07, 0x08) |
| **P2P Transport** | TCP + TLS between oracle nodes |
